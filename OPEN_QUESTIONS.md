# Open questions and assumptions

## M3 — TUI

- **Rendering choice (superseded by the TUI redesign below):** M3 originally used native selects/alerts. The current implementation uses custom theme-aware OpenTUI dialogs with the same four searchable tabs and navigation, verified on home and in an existing session.
- **Missing read API:** M2 exposes available entries but not marketplace catalogs. Add a read-only `listSources` RPC to display/remove catalogs in Sources. The TUI accesses all skillz state through the typed RPC contract; no core/store imports or state-file access.
- **Override approval scope:** M2's `confirmOverride: true` approves *all* overridable collisions in that source, not only the first reported collision. The confirmation must explicitly say that. Per-ID approval tokens and protection against a source changing between preview and install remain a protocol/hardening question for M4.
- **Authentication:** accept an environment-variable *name*, never its value. Default HTTP auth is `Authorization: Bearer <env value>`; optionally allow a custom header/prefix or query parameter. No secure-store integration or masked secret entry is attempted.
- **Preview freshness:** inspect an entry via `listAvailable({ sourceId })` immediately before presenting its source, skills, version and licence. Missing metadata is displayed as unknown/not declared, never invented. A source may change before install because M2 has no preview-bound install token.
- **Updates:** explicitly check via `checkUpdates` on opening Installed and through its refresh action; don't add timers/scheduling (M4). These checks fetch upstream content and may take time. Failed checks are not equivalent to “up to date”.
- **Removal (superseded by safe source deletion below):** the original `remove` RPC forgot the source and cascaded catalog children. The current protocol separates installed removal from explicit source remove/keep policy. Local source files remain untouched.
- **Out of scope inherited from SPEC:** secure auth storage beyond env references; reliable origin classification for every OpenCode skill source; scheduled updates/hardening (M4).

## M4 — scheduler and hardening

### Decisions and assumptions

- **Schedule semantics:** default startup (after built-in skill discovery) and every 6h while OpenCode runs; `updateIntervalMs` is configurable (1000–2147483647), and `automaticUpdates: false` disables automatic installation, not version checks. Due times persist, so location setup/restarts within an interval do not repeat checks. There is no OS/background scheduler when OpenCode is stopped.
- **Singleton/config precedence:** one ref-counted timer per data directory in each process, plus `scheduler.json` running-owner/next-run claims under the existing `.lock` across processes. The first active location's options win within a process; across processes, the first due claimant wins. Configure consistently at user scope. Live owners are not evicted by age; dead scheduler owners recover on the next tick. PID reuse or a permanently stuck live process may require stopping that process and restarting; no distributed lease/heartbeat service is introduced.
- **Pins and source scope:** automatic updates never move `ref` (including a branch), `sha` or `sha256` sources; explicit manual updates may follow a moving ref. Checks still show moving-ref availability. Scheduler cycles check/update installed sources, not catalog refresh or new installs. A new automatic collision skips the whole source and records Errors; previous approved overrides remain approved.
- **Rollback boundary:** remote cached versions and registration snapshots roll back on failed fetching, validation, registration/reload or pointer writes. Linked local files are controlled by their owner and cannot be restored by skillz after external edits. Safe deletion now retains historical caches and deletes only unshared current entry versions; no historical cache-retention policy is added.
- **Filesystem trust boundary:** archive links/special entries and pre-existing extraction/index destination symlinks are rejected; discovery rejects source escapes, including supporting-file and explicit `SKILL.md` symlinks. Cache/state directories and linked local sources must be user-controlled. Same-UID concurrent filesystem tampering/TOCTOU races are not sandboxed. Cleanup makes only managed cache/staging directories owner-writable before deletion, never local source directories.
- **Network/secret policy:** initial HTTP remains supported for the public localhost gateway, but all redirects must be HTTPS, including loopback. Index fetches/redirects stay same-origin. Auth uses env-name references only; auth values are not copied into config/state and are redacted from persisted issues. HTTP/archive responses echoing the configured auth value are rejected. This is not a general-purpose secret scanner for unrelated secrets already present in upstream content or user files.
- **Git execution:** git/SSH and existing credential helpers are trusted local programs, not a sandbox. Downloaded scripts/hooks are never run; checkout disables configured smudge/process filters, hooks and filesystem monitors, and unsupported remote-helper URL schemes are rejected. Licences and downloaded bytes are unchanged, ordinary executable modes preserved, and archive privilege bits stripped.
- **Preview/approval remains source-wide:** M3's explicit Yes approves all overridable collisions in that fetched source. No preview-bound digest/approval token or per-ID approval protocol was added; an upstream may change between preview and install. Use immutable SHA/SHA-256 pins when that matters. Automatic updates never use approval prompts.

### Remaining questions and limitations

- **Cross-process registry visibility:** shared-file claims prevent duplicate scheduled work across standalone servers, but registration broadcasts currently cover locations only within one server process. A separately running server retains its previous registered snapshot until plugin reload/restart after another process updates shared state. A state-watcher/reconciliation protocol remains future work; the normal shared OpenCode server path synchronizes all its active locations sharing a data directory. The TUI being a different process does **not** itself create this limitation: its `context.client.rpc(SkillzRpc)` calls execute on its connected server, not in a TUI-local registry. See the existing-session investigation below.
- **Dependency audit:** M4 upgraded the compatible Solid dev dependency to 1.9.18 and overrides only the pinned SDK's Zod with the direct patched 4.6.7 dependency; required type/build/unit/real-TUI checks verify compatibility. High/critical Zod/Seroval advisories are removed. `npm install` still reports 24 moderate transitive advisories in the pinned SDK/npm utility graph. Broad SDK upgrades or major transitive overrides remain a separate compatibility/remediation decision, not a claim of a clean audit.
- **Inherited product questions:** secure auth storage beyond env references; fully reliable config-versus-filesystem origin reporting; packed/published npm installation; large/narrow/accessibility TUI cases; live authenticated HTTP TUI and remote reconnect/multi-client behavior remain unverified as noted in M3. Home-screen invocation is resolved; live session-screen invocation was subsequently verified below.

## Existing-session skill visibility — OpenCode 2.0.24 investigation

- **Reported symptom not reproduced on one server:** a globally configured plugin, real open session, separate tmux TUI attached to that session and local mock provider verified installation through `/skillz`. The very next outgoing model request included the new skill in a system-reminder. The same session received update/disable/enable/remove notices, including mutations at another active location. This is not a new-session-only host cache. The original reporter's particular server topology/model response was not available for inspection; do not claim its exact cause is established.
- **Runtime evidence:** the installed 2.0.24 executable embeds `SkillInstructions.load`, `SessionContext.select` and the registry implementation. `SessionContext.select` calls `skills: h.load(O)` using current permission rules; `SkillInstructions.load` reads `Skill.list`, filters missing descriptions and `autoinvoke === false`, and uses instruction key `core/skill-guidance`. Its initial renderer produces `<available_skills>`. Its change renderer explicitly produces **“New skills are available in addition to those previously listed”**, a replacement list for changed name/description, or **“The following skill IDs are no longer available and must not be used”**. OpenCode preserves the initial instruction prefix and supplies deltas in later model context. That reminder is evidence the existing session has refreshed, not evidence that a new session is required.
- **Reload audit:** `SkillRegistration.replace` disposes its old transform, installs a snapshot transform and awaits `ctx.skill.reload()` plus a visibility check. `setup` activation applies this to every member of the data-directory location group, rolling back all locations on failure. Install, update, enable/disable, removal and cascading source removal use this activation path; only startup deliberately skips list/reload until built-in discovery completes. Unit coverage now explicitly asserts a reload in both active locations for each mutation.
- **API research:** the pinned `@opencode/plugin` Promise typings expose skill `list`, `transform`, `reload`; registration disposal; `session.hook('context', ...)` with mutable system/messages/tool definitions; and subscribe-only host events. Runtime `reload` invalidates/replays active transforms and publishes `skill.updated`; it does not rerun setup, reread external skillz state in other processes, or rewrite an in-flight request. No extra session refresh or manual bus publication is needed. A context hook could alter outgoing instructions but would duplicate the host's permission-filtered guidance rather than fix a demonstrated cache bug. Custom RPC events are not cross-server registry broadcasts.
- **Documentation checked:** [V2 skills](https://opencode.ai/v2/docs/skills) documents listing at each model step; [server plugins](https://opencode.ai/v2/docs/build/plugins/server) documents transform/reload and context hooks; [plugin overview](https://opencode.ai/v2/docs/build/plugins) and [RPC](https://opencode.ai/v2/docs/build/plugins/rpc) document server/TUI separation and connected-client dispatch. These are rolling docs: the installed 2.0.24 typings/executable and real wire-request experiment are the version-specific evidence, not an assumption that all current documented APIs exist in 2.0.24.
- **User-facing change:** success toasts now say **“sessions on this server refresh next model step”** for install/update/enable/disable/remove, including cascading source removal. README explains reminders, permission/autoinvoke filtering, in-flight requests and separate-server limitations. Saying “Available in new sessions” would be incorrect for the verified normal path.
- **Remaining limitation/upstream scope:** no host per-session cache workaround is warranted by this reproduction. A model can overlook an advertised skill or repeat the original list; this test verifies sent context, not autonomous invocation by a paid model. Separate running servers sharing disk still need reconciliation in skillz; no watcher or cross-server bus was added here. Already-loaded skill content is not erased from transcript on update/removal. Other providers, reconnects and compaction were not tested in this investigation.
- **Repeatable verification:** build first, then `OPENCODE_SESSION_SMOKE=1 npm test -- test/session-runtime.test.ts`. The test uses disposable HOME/XDG directories under `/tmp/opencode`, a dedicated tmux server, an authenticated private OpenCode server and a loopback mock OpenAI-compatible provider. It needs no user account, makes no real LLM calls and removes its own state/processes. It checks the newest guidance rather than mistaking a historical notice for a fresh update.
- **Checks after the investigation:** `npm run typecheck`, `npm test` (185 passed, 4 opt-in tests skipped), `npm run build`, the real session-refresh smoke (1 passed) and the existing real-TUI smoke (1 passed). No commit was created.

## TUI redesign — theme-aware rendering and source trust

### Research and decisions

- **Version-specific API:** checked the installed `@opencode/plugin@2.0.24` TUI context typings and the [V2 plugin overview](https://opencode.ai/v2/docs/build/plugins) / [TUI guide](https://opencode.ai/v2/docs/build/plugins/cli). Native select titles/descriptions/footers and alert messages accept strings, not style props. `dialog.show(render, onClose)`, `dialog.set`, scoped keymap layers, `context.renderer` and `context.theme` are available in the pinned API. Rolling docs describe newer OpenTUI versions too; they were not used to assume a newer runtime contract.
- **Custom rendering:** `src/tui/render.ts` creates OpenTUI Box/Text/Input/ScrollBox renderables in the host's Solid dialog owner. The pinned real CLI accepts those renderables as Solid children, so no JSX compiler or second Solid/OpenTUI runtime bundle is needed. OpenTUI 0.5.14 and theme 2.0.24 declarations are dev dependencies, OpenTUI core is a peer, and imports resolve to the host at runtime. The adapter is loaded lazily when `/skillz` opens. Controller/model stay independent of native renderer imports and use typed RPC only.
- **Colours:** all colours are semantic `context.theme` values (`text.feedback.success/error/warning/info.base`, `text.muted`, `text.base`, raised/formfield backgrounds). No fixed hex/ANSI palette is shipped. Selected rows use `background.raised.high`, not `background.action.primary.selected`: migrated V1 themes intentionally make the latter transparent. Bold labels plus `›` indicate focus without colour. Positive actions use success, removal/disable/No use error, update/override warnings use warning; installed badges are independently coloured. Theme reads run in a Solid effect; the user's theme is not overridden.
- **Confirmations:** one screen with read-only source/trust/skills/count/version/licence, followed by Yes first and No second. No starts focused; arrows/Tab change focus, Enter activates the focused choice, Escape/host dismissal cancels. No search input or selectable metadata appears on confirmation screens. Collision details name the existing ID/origin, explain source-wide override approval, precedence, untouched original and restoration after removal. Removal explains managed-state/cache scope and that local files remain untouched. Details use a bounded scroll pane (PgUp/PgDn or mouse wheel) above the choices.
- **Trust display:** existing persisted `parentId` distinguishes explicitly added root sources from generated marketplace entries. Roots display “Trusted — you added this source”; generated entries conservatively display their actual upstream and “Not added by you — from marketplace X”, including same-host entries. An exact raw source identity (type/location/subpath/pins) matching an independently added root also counts as explicitly added; matching sanitized display strings or only host names does not. Removing the explicit record removes that trust, unless another matching explicit record remains. Disable does not untrust. This is display/provenance only: no per-skill trust, execution permission, flags, allowlist or new state schema. SPEC security requirements are unchanged: preview source/skill list and never execute downloaded content during install.

### Open questions and limits

- **Inheritance policy:** should same-repository/local-relative entries inherit the marketplace's trust in a future product iteration? Current wording is deliberately conservative: only explicit root identities are trusted, never arbitrary repositories merely sharing a host. Existing state does not record whether a root came from the TUI or another intentional `addSource` RPC caller; both are treated as user-added. No dedicated trust flag is warranted for this display-only request. A future policy that actually gates scripts/execution would need a separate explicit trust/revocation model and security review, not reuse this UI label as an authorization boundary.
- **Preview freshness/approval scope:** unchanged from M3/M4; no digest-bound preview token or per-collision approval token. Explicit override approves all overridable collisions in that fetched source. Prefer immutable pins where needed.
- **Layout coverage:** automated adapter tests cover focus, arrows/Tab/Shift+Tab, Enter/Escape/dismissal, mouse-choice handlers, filter/footer actions, colour-token selection and badge colours. Real TUI probes run at 150×48 with the default theme; extreme catalogs, small terminals/resizing, arbitrary light/custom themes, assistive technology and real mouse interaction are not comprehensively visually tested. Scroll heights estimate wrapped lines; there is no claim of exhaustive Unicode-width/layout coverage. Very long details are scrollable rather than silently truncated.
- **Dependency environment:** the pinned OpenTUI package advertises Node >=26.4 or Bun >=1.3, so installing dev dependencies on the current Node 22 prints an engine warning. Build/typecheck and Node tests pass (renderer tests mock native bindings); the real renderer runs inside OpenCode's Bun host. This does not change the core/server Node requirement. npm reports the same 24 moderate advisories, with no new high/critical findings. `@opentui/solid@0.5.14` was researched but not added: its exact Solid 1.9.12 peer would conflict with the already-patched 1.9.18 dependency; imperative renderables avoid that unnecessary dependency/JSX pipeline.

## Non-blocking tab opening and persisted update status

- **Supersedes M3's blocking Installed check:** tab opening now awaits only local read RPCs. `updates.json` stores `{ checkedAt, updates }` with the existing typed per-source update result (installed/latest version, availability, issues). Atomic replacement and the state lock protect writes; known auth values are redacted before persistence. Only the server/core Store writes the cache, never the TUI. Startup, interval, manual-only scheduler checks and manual checks all use this path. `listUpdateStatus` is read-only and JSON-safe; it reconciles cached results with current installations, hides obsolete results and returns a null timestamp when any installed source lacks a matching result.
- **Freshness:** Installed refreshes in the background when status is missing or at least ten minutes old. Ctrl+R forces a background check regardless of freshness, but joins an existing check rather than overlapping it. Cache age, checking and failure hints are muted. Fetch failures persist per-source issues and enter Errors; unexpected manual RPC check failures are logged best-effort. If the server is unreachable, the TUI cannot write its server-side Errors log; it displays the local failure hint without an alert/toast.
- **Tab-path audit:** Installed previously awaited `checkUpdates` before even reading/rendering its list. Discover and Sources did not intentionally fetch on entry, but the shared `load()` called `discoverAvailable()` whose no-ID cache read took the same lock as long-running network mutations, so all tabs could indirectly wait for network. No-ID available listings now bypass that lock and use persisted source/catalog metadata. Discover and Sources render those cached rows, then share a background catalog refresh; an empty list shows a loading row. Errors remains local-only on entry, and Ctrl+R now reloads that log rather than refreshing unrelated catalogs. Explicit Discover Enter still fetches a full preview before confirmation; source/install/update/remove actions are not silently backgrounded.
- **Rendering lifetime:** updates repaint the mounted custom list rather than reopening the dialog. The input, filter, selected source identity, footer focus and scroll offset are retained. The renderer buffers an initial update until the host mounts its lazy dialog. View-generation checks ignore results after tab switches, entry/detail selection, dismissal or plugin cleanup. Background work can still complete on the server and populate the shared cache after the view closes.
- **Dedupe boundary / remaining question:** checks and catalog refreshes join one in-flight promise per data directory across all locations/module reloads in one server. Different standalone server processes serialize through the existing state lock but do not join each other's promises; a queued manual check may run after the other server's check. Should future cross-process manual requests coalesce as well? Existing scheduled-cycle claims already suppress duplicate scheduled work. No distributed promise/lease protocol or registry watcher was added.
- **Catalog freshness / remaining question:** source/catalog data is already persisted in `sources.json`; the ten-minute catalog refresh throttle is manager-local rather than a new persisted catalog timestamp. Reopening the same manager retains its throttle, but a new TUI may refresh the cached catalog again. Should a future catalog-specific status RPC persist a refresh timestamp? The current requirement to show local data first is met without changing catalog identity/storage.
- **Live coverage:** the terminal smoke holds an actual loopback HTTP update response open, asserts Installed rows and “checking…” are already visible while it is pending, then releases it and verifies fresh badges in that same dialog. No production-only delay/test hook is needed. Renderer tests cover input/identity/action-focus/scroll preservation and empty loading/failure states; controller tests cover fresh/stale cache, forced checks, in-flight dedupe, quiet errors, closed-dialog results and Discover/Sources refreshes. Store/RPC/scheduler tests cover persistence, lock-free reads during a slow check, failed-check logging, JSON safety and manual-only cache population.
- **Final verification:** `npm run typecheck`, `npm test` (208 passed, 4 opt-in tests skipped), `npm run build`, `OPENCODE_TUI_SMOKE=1 npm test -- test/tui-runtime.test.ts` (1 passed), and `OPENCODE_SESSION_SMOKE=1 npm test -- test/session-runtime.test.ts` (1 passed) all passed in one final sequential run with disposable HOME/XDG directories under `/tmp/opencode`. The TUI startup probe now waits for the slash-command suggestion before sending Enter to avoid a registration/autocomplete startup race observed during an earlier concurrent smoke run. Existing uncommitted changes were retained; no commit was created.

## Safe source deletion and abandoned installations

- **Protocol and presentation:** `previewRemoveSource({ sourceId })` returns the exact affected installed entries, skill count and revision. `removeSource({ sourceId, skills: 'remove' | 'keep', revision? })` requires an explicit policy, including for core callers. Sources shows read-only source name/location and each origin/skill pair above red remove-all, yellow keep-as-abandoned and default-focused Cancel; Escape cancels. No installed skills uses the ordinary safe-default Yes/No dialog. The TUI binds removal to the preview revision, so concurrent changes require review again. Other API callers may deliberately omit the revision; they still must choose a policy.
- **Persistence and detachment:** `installed.json` keeps its existing source-ID-keyed entries and `scope: 'user'`. Optional `upstream` records the resolved source, with the installed git SHA/archive digest/version in the existing `version` field. Keeping skills adds `abandoned: true` and `formerSource`, retaining that immutable origin ID, cache files, overrides/order, entry enablement and individual `disabledSkills`. A retained source ID is provenance, not permission to fetch. Abandoned entries are omitted from checks/status/scheduling, reject manual updates, stay registered if enabled, and remain removable/toggleable. Source-level toggles and individual skill toggles are supported; the entry-level switch still gates all its skills.
- **Exact deletion:** catalog children are selected only by recorded `parentId`; installed entries only by their exact recorded source ID. Independently added identical upstreams and other sources' same-ID skills survive. Installed `remove({ sourceId, skillId? })` never cascades or forgets source configuration. Single-skill removal retains an `excludedSkills` list so later updates do not silently reinstall it. Reinstalling the whole entry after removing it resets exclusions.
- **Cache boundary:** only an explicitly owned, current `cache/<origin-id>/<version>/` directory is eligible. Every cache ancestor is checked with `lstat`; cleanup does not follow links. Recorded local sources are always unlinked, including legacy local links resolving inside cache. Missing ownership, unsafe paths and historical versions are retained. Any remaining/abandoned entry referencing that directory, including via its skill files, protects it. Local/external/config-path files are never removed. Cache/state must remain user-controlled; the existing same-UID TOCTOU limitation remains.
- **Commit/rollback:** under the shared state lock, a transient atomic `removal.json` journal records previous/next source metadata and the next installed snapshot. Registration/reload verification across all active locations precedes the atomic installed-pointer commit. Failure restores source metadata and registrations before touching cache. Startup/next writer recovers interrupted metadata by comparing the authoritative installed pointer with the journal. Cleanup happens only after commit; a cleanup failure is reported in Errors and via RPC, leaving skills consistently unregistered rather than resurrecting pointers to partially deleted files. Recovery may retain unused cache. Automatic updates recheck both live source membership and installed/abandoned state inside the lock, so stale scheduled check results cannot resurrect a removed source or installed entry.
- **Re-adoption implemented:** direct re-add, or marketplace refresh after re-add, reattaches an abandoned entry without fetching/reinstalling or changing its installed version, enablement, exclusions or priority. Match requires exact origin ID, upstream identity (including subpath/pins), skill selection and declared version. Retargeted marketplace names are not adopted. Re-adoption activation failure leaves the entry abandoned.
- **Open policy question — broader re-adoption:** should a changed declared marketplace version or skill-selection ordering count as the same identity? Current matching is intentionally conservative and will not reattach those changes. No fuzzy matching by name, skill ID or host is used.
- **Open maintenance question — cache GC/retry:** historical versions, unknown ownership, shared cache directories and post-commit/interrupted cleanup leftovers are retained conservatively. There is no separate ownership-audited GC or cache-cleanup retry command yet. Repeating source deletion is idempotent and does not sweep orphan folders or delete already-abandoned entries.
- **Existing limitations remain:** source scopes beyond user, cross-standalone-server registration broadcasts, immutable snapshots for local links, and same-UID concurrent filesystem tampering remain outside this change. Source removal synchronizes all locations on the connected server, not other standalone servers.
- **Coverage:** `test/removal.test.ts` covers both policies, duplicate skill IDs from two catalog entries, independently added identical upstream, external/config sentinels, shared abandoned-cache references, individual removal/exclusions, local/legacy-local/symlink/unowned paths, required policy, stale previews, checks and stale scheduled updates racing deletion, automatic re-adoption, state-write rollback, crash metadata recovery and post-commit cleanup failure reporting. Plugin tests cover individual abandoned toggles/removals, correct override fallback in two active locations and later-location reload rollback for both policies. Lifecycle tests validate explicit policy/typed RPC shape; controller and renderer tests cover exact previews, both branches, safe defaults, cancellation, colours and abandoned hints.
